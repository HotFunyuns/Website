# Authority audit

A page-by-page baseline of every route the site exports, with the specific
authority, trust and technical gaps found on each.

Measured **2026-08-13** against the `out/` directory produced by
`npm run build` (Next.js 14.2.35, static export).

The issue registers below record the site **as found**. Every row now carries a
status; what was actually changed, and what was deliberately left alone, is in
[§ Resolution](#resolution) at the end. The baseline numbers are not rewritten —
they are the only "before" reading that exists.

## What this document does and does not contain

Everything below was measured from the repository or the exported HTML. Where a
number appears, it was counted, not estimated.

**No third-party Page Authority, Domain Authority, Trust Flow, Citation Flow or
equivalent score appears anywhere in this file.** Those are vendor-modelled
numbers, they are not observable from this repository, and inventing them would
make the rest of the audit untrustworthy. Where external authority matters, the
audit says what to measure in Google Search Console instead.

No search volume, keyword difficulty or traffic projection appears here either.
`docs/keyword-verification-needed.md` is the register for terms that still need
checking in a real keyword tool.

**Correction to L2.** Adding blog categories to the footer was proposed and then
rejected. Seven more site-wide links would give every blog category hub the same
inbound count as the homepage, flattening exactly the distinction the hub-and-spoke
structure is meant to create, and the link report already flags each category name
as ambiguous anchor text because it exists in both the app and blog trees. Doubling
that ambiguity site-wide is a cost with no matching benefit. Only `/blog/` was
added to `exploreLinks`; `/press/` was added at the same time so the new page is
not born an orphan.

**Correction to L3 and L4.** These were logged as linking defects. They are not.
Every one of the five articles involved sits in a category holding one or two
*published* pieces — and in each case the genuinely related articles exist, are
written, and are gated as drafts. `android-video-player-guide` is the clearest
example: it is the only published `video-utility` article, so its two
`relatedArticles` entries were filled with an education article and a history
article because there was nothing adjacent to point at.

The available fixes were all worse than the problem: manufacturing cross-category
links dilutes the signal with false adjacency, and publishing a draft to fix a
link count is prohibited. **Left as found, deliberately.** The correct resolution
is that these counts rise on their own as drafts publish, and each draft's release
checklist should include repointing the placeholder entries in
`android-video-player-guide`. Nothing here is worth changing before then.

| `/apps/82-0-pro-basketball-draft/` | Legacy URL for a renamed app | `noindex, follow`, canonical to `/apps/pro-basketball-draft-gm-mode/`, meta-refresh, no-JS fallback body | **T9** — drop the `noindex`. Do not link. Keep out of the sitemap. |
| `/404.html`, `/404/` | Not-found | `noindex`, but inherits the homepage title, description and `canonical: '/'` | T5 |

Static export cannot serve real 301s, which is why the retired app URL is a
canonical + meta-refresh stub. That is the correct approach for this hosting
model — but the `noindex` that sat alongside it was working against it. A page
Google is told not to index is a page whose canonical Google does not process, so
the stub was absorbing whatever the old URL had earned instead of passing it to
the renamed app. The refresh still moved human visitors, which is why the fault
was invisible.

With `noindex` removed, the expected Search Console outcome is
*"Alternate page with proper canonical tag"*. If the URL is instead indexed as a
page in its own right, the change did not work and `noindex` should come back.
That check is in `docs/authority-measurement-90-day.md` §7.

## Priority order

Ranked by expected authority effect per unit of risk. Nothing here changes a
live URL.

1. **L1** — app category hubs link to no articles. The single largest structural
   gap: seven hub pages at depth 1, each with strong inbound equity, passing
   none of it to the content that supports their topic.
2. **E1** — undisclosed ads and in-app purchases in three articles. A trust
   defect, and the one item here that could reasonably be read as misleading.
3. **T1** — sitemap `lastmod` accuracy. Cheap to fix, and false freshness on
   two-thirds of the sitemap actively devalues the signal for the third that is
   honest.
4. **L2, L3, L4** — footer blog access and article-to-article linking.
5. **T2, T3, T4, T5, T6** — title lengths, missing `og:image`, one long meta
   description, 404 metadata, breadcrumb consistency.
6. **E2–E6** — sourcing and limitations gaps.
7. **C2–C5** — cannibalization work that only matters at draft publication time,
   handled per batch rather than now.

This ordering was written before the issues were worked and is left as it stood.
It was wrong about one thing, and the miss is worth recording: **E3** was ranked
in band 6 as a citation-precision nit and turned out to be the most serious
finding in the audit — wrong figures, in 11 files rather than 5. The lesson is
that "the citation is imprecise" and "the number is wrong" look identical until
someone opens the source, so verification has to come before triage, not after.

## Method

- Link graph, inbound counts, depth and orphan status: `npm run report:links`,
  which walks the exported `out/` directory. Body-only outbound counts were
  measured separately from the `<main>` element to separate editorial links from
  navigation.
- Titles, descriptions, canonicals, `og`/`twitter` tags, `img` attributes,
  heading structure and JSON-LD: parsed from all exported HTML files — 68 for the
  baseline, 69 after `/press/` was added.
- Image encodings: WebP RIFF chunk types read directly from `public/icons`
  (`VP8L` lossless, `VP8 ` lossy), with per-page eager-vs-lazy byte totals
  resolved against the exported markup.
- Article metadata, related-article counts and source counts: read from the
  parsed frontmatter of all 75 markdown files.
- App facts: `src/data/apps`, populated by `scripts/verify-play-listings.mjs`
  from the live Play listings and never hand-edited.
- Draft containment: 54 draft slugs checked against emitted routes,
  `sitemap.xml`, `blog/rss.xml`, `llms.txt` and the full text of every exported
  page.
